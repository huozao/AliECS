# 浏览器抓取任务的探测证据契约（改任一采集器前必读）

webdock2 上有**三个相互独立的 Chrome**，分属三个仓、三条发布链，各写各的日志。
本文是它们的共同下限：一次抓取失败时，**不登设备就能判断失败在哪一步**需要哪些证据。

> 2026-09-09 立。当天一次 ChatGPT 抓取故障暴露的问题不是没日志，而是**三个采集器
> 对"什么算证据"的理解完全不同**：额度采集器每次都留截图和结构化记录，飞书原文同步
> 一张截图都没有，ChatGPT 侧留了截图却送不出设备。定位因此从"读日志"变成"逐台 SSH"。

## 三个采集器的位置

| 用途 | 仓 | 容器 | CDP | 显示器 / noVNC | profile |
|---|---|---|---:|---|---|
| ChatGPT 生产浏览器 | `webdock` | `webdock` | 9222 | `:99` / 6080 | `/app/browser_data` |
| 飞书文档原文同步 | `feishu-obsidian-miner` | `webdock` | 9223 | `:100` / 6081 | `/app/browser_data/feishu-sync` |
| AI 额度采集 | `ai-quota-monitor` | `quota-monitor` | 9224 | 容器自带 | 容器自带 |

前两个共用 `webdock` 容器但**是两个独立 Chrome**，第三个在另一个容器里。
⚠️ 容器里的进程名都是 `chrome`（即使启动路径是 `webdock-chrome`），只能靠
**profile 路径 + CDP 端口**区分，不能用 `pgrep -x` 认。

## 一、每次抓取都要落一条结构化记录

`ai-quota-monitor` 的 `captures` 表是目前唯一完整的实现，字段按它对齐：

| 字段 | 含义 | 为什么不能省 |
|---|---|---|
| `provider` / `task` | 哪个采集目标 | 一个采集器往往抓多个目标，失败要能说清是哪一个 |
| `captured_at` | UTC 时间戳 | ⚠️ 容器多数不设 TZ、跑在 UTC，宿主是 CST。**只存归一化后的绝对时间**，下游不得再解析页面上的字符串 |
| `url` | 实际停留的 URL | 「以为在 A 页其实在 B 页」是最常见的静默失败 |
| `status` | `healthy` / `schema_changed` / `network_error` / … | 见下方判据一节 |
| `confidence` | 0–1，解析到多少个预期字段 | 区分"抓到了"和"抓到了但只剩一半" |
| `fields_json` | 解析出的结构化结果 | 事后能重放判定逻辑，不用复现页面 |
| `error` | 失败原因原文（截断） | |
| `screenshot_path` + `screenshot_sha256` | 截图与其哈希 | 哈希用来判断"两次失败是不是同一个页面"，比肉眼比对可靠 |

## 二、截图：成功也截，失败必截

- **失败必须截图**，并且截图动作本身要有独立超时（额度采集器用
  `QUOTA_SCREENSHOT_TIMEOUT_SECONDS`，默认 15s）——页面卡死时 `page.screenshot()`
  会一起卡住，没有超时就把失败拖成挂起。
- 截图失败**不能吞掉原始错误**：把它并进 `error` 字段（`原错误 | screenshot: ...`），
  不要让取证失败替换掉真正的失败。
- 截图要能**离开设备**。留在容器里的截图等于没有：`webdock` 一直在写
  `screenshot.png`，但直到 2026-09-09 才通过既有 media store 发布成短时 URL 送进
  飞书卡片。新采集器不要自建投递通道，走各自链路上已有的那条。

## 三、判据落在结果上，不落在动作上

- **"操作发出去了"不是判据**。点击一个列表项，点错行同样会"成功"——判据必须是
  结果状态里那个唯一标识（URL 里的 id、页面上的目标字段），不是点击本身。
- **相等，不要包含**。`lark-hao` 是 `lark-hao2` 的前缀；包含匹配会静默选中另一个
  对象，然后返回一条看起来合理、其实来自错误上下文的结果。
- **别用尺寸、坐标、位置这类近似量定位元素**，它们会在下一种样本形状上静默失效
  （`webdock/AGENTS.md` 有 2026-08-20 的实例）。可用的结构锚：稳定的 `data-*` 属性、
  `aria-haspopup` 这类语义属性。
- **`aria-label` 和任何界面文案都是本地化的**。webdock2 是 en-US、webdock1 是
  zh-CN，同一个按钮两台机器两个名字——按文案选会在其中一台上静默选空。文案只能
  当白名单兜底，不能当唯一判据。
- **0 命中要能区分"判据为假"和"这次根本没测到"**：断言先在一个已知正常的对象上跑
  一遍，跑不出预期结果说明是断言坏了，不是被测对象坏了。

## 四、证据要有保留期

- 每条记录带 TTL，过期连同截图一起删（额度采集器 `QUOTA_RETENTION_DAYS` 默认 7 天）。
- ⚠️ 反例：`webdock` 的 `logs/debug/` 无保留期，2026-09-09 已积到 59 个目录，
  没有任何机制会提醒。新采集器不要复制这个形态。

## 五、失败要说清"哪台机器、第几次尝试"

- 有主备/重投的链路，**每次尝试都要留下 route + device + error_code**，失败上报时
  列成一条链。只报最后一次会把排查引到「继承了问题的那台机器」上——2026-09-09
  实例：webdock2 `UPLOAD_FAILED` → 改投 webdock1 → `BROWSER_NOT_STARTED`，
  卡片只显示后者。
- 设备名不能只在成功路径写。`webdock_footer` 就是只在成功时填，导致最需要设备名的
  失败卡片反而没有。
- **错误消息要说真话**。硬编码一句"看起来最像"的原因（`Chrome not running or CDP
  attach failed`）会把排查带偏一整轮：当天两台机器的 Chrome 和 CDP 都是好的，真正
  失败的是 attach 之后的 `page.goto`。

## 六、下游判据不要绑在人类可读文案上

`webdock-failover-proxy` 曾用 `"Chrome not running or CDP attach failed" in text`
决定要不要切备机。上游一改文案，它就**静默不切且不打日志**。跨组件判据一律用结构化
字段（`error_code`），文案匹配只作为跨版本兼容的兜底。

## 现状与差距（2026-09-09 盘点）

| | webdock (9222) | feishu-miner (9223) | quota-monitor (9224) |
|---|---|---|---|
| 结构化记录 | 部分：`selector_report.json` 散落文件 | ❌ 仅文本日志（`utils/logger.py` 的 `Reporter`） | ✅ SQLite `captures` |
| status / confidence | ❌ | ❌ | ✅ |
| 失败截图 | ✅ 但只在部分路径调用 | ❌ 完全没有 | ✅ 成功也截 |
| 截图能否离开设备 | ✅ 2026-09-09 起 | ❌ | ✅ |
| 保留期 | ❌ | ❌ | ✅ 7 天 |
| 失败通知 | 经 bridge 出飞书卡片 | 统一消息中枢 | 统一消息中枢 |

差距最大的是 `feishu-obsidian-miner`：它是 sync API（`patchright.sync_api`），
接入截图和结构化记录的改动量明显大于另外两个，单独排期。
