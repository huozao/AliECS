# 研发档案：产品研发时间线（首页入口）

> 来源：2026-07-11/12 brainstorming session。仓库：AliECS（backend-api + public-web），走 PR，不直推 main。
> 目标：把企微群研发记录、配色&样品需求单、T+ 系统配方、生产时的色粉记录沉淀为"按产品可追踪"的研发档案——
> 每个产品一条时间线，从最早开发记录到最终成果，带阶段标记，作为 hydwang.xyz 首页的一个入口。

## 0. 已核实事实（生产库实查，2026-07-11；实现时以此为真值起点）

## 1. 架构（方案 A：运行时聚合，零新同步管线）

```
external_records(需求单/研发过程记录/产品名称明细/生产任务/配方单及色彩表现/产品对照表)──┐
group_messages ──────────────────────────────────────────────────────────┼─▶ backend-api
tplus_bom_records ────────────────────────────────────────────────────────┘   routers/rnd.py
                                                                             （运行时聚合，只读）
                                                                                   │
                                                              public-web /rnd/（列表+详情时间线）
```

- **不新增同步管线、不物化事件表**。数据量百行级，现查现拼；现有 doc-sync / tplus-sync 更新后页面自然跟新。
- 产品对齐 = 企微「产品对照表」（编辑面）→ doc-sync → `external_records`（生效面）。延续"表格=编辑面 / DB=生效面 / 单向表→DB"既有模式。

## 2. 组件

### 2.1 企微「产品对照表」（一次性人工建，编辑面）
在「登记表-副本」文档内新建子表，列：

| 列 | 类型 | 说明 |
|---|---|---|
| HYD命名 | 文本 | 对齐产品名称明细.命名，产品主键展示名 |
| T+母件编码 | 文本 | 可多个，逗号分隔（同产品多版本母件） |
| A生产品名 | 文本 | 对齐配方单及色彩表现.品名，可多个逗号分隔 |
| 人工标记 | 单选 | 重点 / 停滞 / 归档 /（空） |
| 备注 | 文本 | |

- 建表可用 wecom-cli 手建一次（同类先例：研发过程记录子表）；建好后 doc-sync 整簿重扫自动纳管，**不需要代码**。
- 填写辅助：`GET /v1/rnd/match-suggestions` 返回未对齐产品 + 按数字核心的候选建议，人工确认后填表。

### 2.2 backend-api：`app/routers/rnd.py`（新，只读）
- 依赖现有 SSO 会话 + `formula` 权限（与配方查询同一 RBAC 检查方式）；未登录 401/403 行为与现有 formula 接口一致。
- 聚合逻辑放 `app/rnd/`（新包：`aggregator.py`、`matching.py`、`time_parse.py`），router 只做装配，符合 main.py 拆域后的结构。
- 按 source 定位不硬编码 source_id：以 `(provider, env_profile, document_name/sheet_name)` 查 `external_sources`，兼容重扫后 id 变化；找不到某源时该源事件缺省为空并在响应里报 `missing_sources`。

### 2.3 API

`GET /v1/rnd/products`
- 产品清单 = 产品名称明细全部行 ∪ 对照表行（并集，HYD命名 为键）。
- 每项：`name`（HYD命名）、`digit_core`（首个数字）、`customer`、`salesperson`、`stage`（见 §4）、`manual_tag`、`latest_activity_at`、`aligned`（T+/A 生产是否已对齐）、`counts`（各类事件数）。
- 支持 `?q=` 名称/客户模糊过滤（后端简单 contains 即可，量小）。

`GET /v1/rnd/products/{name}/timeline`
- `name` = HYD命名（URL encode）。
- 返回产品头信息 + `events[]` 按时间升序；每个 event：`type`、`ts`（ISO，可空）、`ts_raw`、`title`、`detail`（类型相关字段）、`images[]`、`link`（如 T+ 配方事件带 formula 页跳转 URL）、`source`。
- `ts` 解析失败的事件归入 `undated_events[]`，不丢。

`GET /v1/rnd/match-suggestions`
- 对未在对照表登记 T+/A 品名的产品，返回候选：数字核心相等（HYD-3587 → 3587；T+ 母件编码取前导数字段；A 品名取字母后数字段）即为候选。仅建议，不自动写入。

### 2.4 事件源映射（聚合规则）

| type | 源 | 时间取值 | 关联到产品的路径 |
|---|---|---|---|
| requirement（需求提出） | 需求单 1768 | 提交时间 | 产品名称明细.需求单关联（record 链）→ 需求单行；辅以对照表 |
| rnd_node（研发节点） | 研发过程记录 1977 | 时间 | 审批单编号 → 需求单 → 产品 |
| group_message（群讨论，默认折叠） | group_messages | ts | record_id → 需求单 external_record_id → 产品 |
| sample_done（样品完成） | 需求单 1768 | 完成时间 | 同 requirement |
| tplus_formula（T+ 配方定型） | tplus_bom_records | raw_json 内版本/修改日期，无则 last_seen_at | 对照表.T+母件编码 |
| production_order（生产订单） | 生产任务 4887 | 下单日期（交货日期入 detail） | 审批单编号→需求单→产品；生产明细中`产品名称:`数字核心兜底 |
| powder_record（生产色粉记录） | 配方单及色彩表现 34 | 日期 | 对照表.A生产品名 |

### 2.5 public-web：`/rnd/`（新静态页，单文件 + hash 路由）
- **列表视图**：产品卡片网格（沿用首页米色系卡片风格）：命名、客户、阶段徽章、人工标记、最近动态、事件计数小图标；顶部搜索框 + 阶段筛选；"待对齐"产品显示灰色提示角标。
- **详情视图**（`#/p/<name>`）：头部（命名/客户/业务员/阶段/标记/需求单图片缩略）+ 垂直时间线：事件类型彩色圆点 + 图标，图片缩略点开大图，powder_record 展开显示色粉明细表，tplus_formula 带"查看配方"跳 formula 页；群讨论折叠为"N 条群消息"点开展开；页尾"日期不明"分组。
- 图片直接用企微 wdcdn URL，`onerror` 占位图（已知该 URL 可能限流/过期）。
- 移动端单列自适应（现有页面同样处理方式）。

### 2.6 首页入口
- `features` 表插入一行：`title=研发档案`，`url=/rnd/`，`category=生产研发`，`required_permission=formula`。用幂等迁移或 seeds（与现有 feature 迁移先例一致，如 0018_ash_calculator_feature.sql）。

## 3. 关键流程（时间线聚合）

1. 解析对照表 + 产品名称明细 → 产品主档 & 别名索引（HYD命名 → {T+编码集, A品名集, 需求单行集}）。
2. 逐源拉取记录（普通 SQL，按 source 一次全量读，百行级），按 §2.4 归属产品。
3. 时间解析（`time_parse.py`）：优先毫秒时间戳 → ISO/常见中文日期文本（`2026-06-15`、`2026.06.15`、`20250402`）→ 失败置空进 undated。
4. 排序输出。列表页 `latest_activity_at` = 该产品全部事件最大 ts。

## 4. 阶段推导（自动，人工标记独立并存）

```
开发中（有需求单） → 已打样（需求单.完成时间非空） → 已定型（对照表挂到 ≥1 条 T+ BOM）
→ 已量产（有生产订单或生产色粉记录）
```
取满足条件的最高阶段；无任何需求单但有 T+/生产数据的老产品直接按其最高数据源定级。

## 5. 错误处理 / 边界

- 某数据源缺失/为空：跳过该源，响应 `missing_sources` 提示，页面顶部黄条提示"部分数据源不可用"。
- 对照表尚未建/未同步：全部产品按"待对齐"降级展示（只有 B 侧需求/研发节点事件），功能可用不报错。
- 时间解析失败：进 undated，不丢事件。
- 群消息未绑定需求单（record_id 空）：不挂产品，不展示（原始数据仍在 DB，后续绑定自动补上）。
- 同名产品/别名冲突（一个 T+ 编码填进两个产品）：都展示并在两边标"别名冲突"提示。
- 权限：无 formula 权限访问 API 返回 403；前端跳 SSO 登录（与 formula 页 PR#173 后的模式一致）。

## 6. 测试（root tests/，网络与 DB 全 mock）

- 别名索引构建：对照表多值逗号分隔、冲突分支。
- match-suggestions：数字核心提取（HYD-3587黄/0783-NHABSMLZ/40000032/YR1662黄L84）与候选生成。
- 时间解析：毫秒戳/ISO/点分/8位数字/垃圾文本。
- 时间线聚合：七类事件归属、排序、undated 分组、missing_sources。
- 阶段推导四档 + 老产品无需求单分支。
- 权限：无 formula → 403。
- 前端冒烟：现有前端测试模式（如 test_formula_color_space_frontend.py 的做法）覆盖入口渲染。

## 8. 非目标（YAGNI）

- 不做时间线人工编辑/评论（标注面在企微表，不在网页）。
- 不做导出（后续需要可复用 compare_export 真 xlsx 模式）。
- 不接入尚未电子化的数据源；不改动任何现有同步管线与「研发过程记录」写入链路。
- 不做产品对比、统计报表。
