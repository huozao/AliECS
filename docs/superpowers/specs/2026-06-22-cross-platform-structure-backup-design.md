# 跨平台结构备份扩展设计

## 目标

在现有企微 A「企微智能表格结构备份」中完成三项扩展：

1. 将平台、来源、名称、工作表/字段数量、链接等总体字段放在最前面。
2. 将备份文档自身登记到 `企微A-最新结构`，只读取结构，不读取其业务记录。
3. 新增 `飞书-最新结构`，按飞书多维表格应用保存 app_token、table_id、数据表名称和字段结构，并复用 `结构变更历史`。

## 工作表与字段顺序

备份文档固定包含：

- `企微A-最新结构`
- `企微B-最新结构`
- `飞书-最新结构`
- `结构变更历史`

最新结构表的总体字段顺序为：

`平台 → 来源类型 → 智能表格名称 → 工作表数量 → 字段总数 → 来源链接 → 企业配置 → 状态 → 文档定位ID → docid → 唯一键 → 创建来源 → 创建副本请求时间 → 企微修改时间 → 源同步时间 → 备份更新时间 → 结构最后变化时间 → 结构哈希`

其后按 `工作表01...工作表20` 保存名称、编码、类型、可见性、字段结构和字段数量。历史表先放相同总体字段，再放版本唯一键、上一结构哈希、触发来源、结构变化时间，最后放工作表结构。

## 字段重排迁移

企微 API 不支持原地移动字段，只支持改名。因此对字段顺序不匹配的工作表采用受控重建：

1. 读取旧表字段映射与全部记录。
2. 创建临时工作表，重命名默认首字段为目标第一列，再按目标顺序添加其余字段。
3. 按字段标题复制旧记录到临时表并核对记录数。
4. 将旧表改为临时旧名，将新表改为正式名；成功后删除旧表。
5. 任一步失败时保留旧表，不删除已有数据。

## 企微备份文档自身

备份文档登记为 `structure_backup_doc`，其四张工作表登记为 `structure_backup_sheet`。该类型不进入常规企微记录全量同步，只同步字段结构，因此不会递归读取备份行。每日结构任务允许处理该 docid；写入记录只改变数据，不改变结构哈希。

## 飞书结构快照

飞书同步为每个 `app_token` 建立一个 `bitable_app` 文档锚点，所属 `bitable_table` 作为工作表。结构快照规则：

- `文档定位ID` 保存 app_token，`docid` 留空。
- 工作表编码保存 table_id，名称保存数据表名称。
- 字段结构保存 field_id、字段名、字段类型、顺序和已有配置。
- 唯一键为 `FEISHU:<profile>:<app_token>`。
- 结构哈希变化时写入公共历史表。

每日企微/飞书全量同步结束后，为所有企微文档锚点和飞书应用锚点生成幂等结构任务。单个任务失败进入现有持久队列重试，不影响其他来源。

## 验证

- 单元测试覆盖目标字段顺序、受控迁移、企微自录、飞书分组快照和跨平台写入。
- 本地运行聚焦测试、根测试、T+ 子项目测试、Python 编译、版本和 compose 校验。
- 线上迁移后回读四张工作表，核对字段顺序、A/B/飞书行数、备份文档自身行和历史幂等性。

## 非目标

- 不安装或配置 wecom-cli。
- 不处理 s3 URL 到 dc docid 的恢复。
- 不读取或备份企微/飞书业务记录内容。
