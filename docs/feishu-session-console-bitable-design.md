# 飞书 ChatGPT 会话管理台 —— 多维表格设计

> 轻量阶段方案：**一个 ChatGPT 项目**管理全部飞书会话；每个用户 / 群对应该项目里**一条或多条**独立 ChatGPT 对话；用**一个飞书多维表格（内含多张数据表）**维护 open_id / chat_id / 对话标题 / 对话链接 / 消息日志 / 回复任务。群消息全量记录，但服务器二次判断 `mentions`，**只有 @ 机器人的消息才进入 ChatGPT 处理流程**。

本设计同时是当前线上「飞书 `/新对话` 不在项目里新建对话」问题的根治方案——见末尾「§11 与现有运行系统对接」。

---

## §0 推荐命名 & 数据表清单

**多维表格名称**：`飞书 ChatGPT 会话管理台`

**数据表（一个多维表格内 6 张表）**：

| # | 数据表 | 角色 | 一句话 |
|---|--------|------|--------|
| 1 | 用户表 `users` | 主数据 | 谁能用、是谁、额度 |
| 2 | 群表 `groups` | 主数据 | 哪些群、什么规则 |
| 3 | 会话索引表 `sessions` | **中枢** | peer ↔ ChatGPT 对话链接的唯一映射 |
| 4 | 消息日志表 `message_logs` | 流水 | 所有飞书消息（含不处理的群消息） |
| 5 | 回复任务表 `reply_tasks` | 流水 | 只存真正要送 ChatGPT 的消息 + 回复 |
| 6 | 规则配置表 `rules` | 配置 | 全局 / 群 / 用户 / 会话级开关 |

> 当前阶段坚持「一个多维表格、多张数据表」：单表内表间关联（关联记录 / 查找引用）开箱即用，无需自建外键。拆分时机见 §10。

## §1 session_key 命名规则（核心约定）

`session_key` 是会话索引表的业务主键，也是服务器路由用的 key。

| 会话类型 | session_key 格式 | 示例 |
|----------|------------------|------|
| 私聊 | `tenant_key:user:open_id` | `2d…f3:user:ou_28d4f058cbd2a13f3fcc6fd575023e8e` |
| 群聊（群级共享一条会话） | `tenant_key:group:chat_id` | `2d…f3:group:oc_6510eb384d8c43671d7c3a84ffcc897a` |
| 群内个人（同群每人独立会话） | `tenant_key:group_user:chat_id:open_id` | `2d…f3:group_user:oc_6510…:ou_28d4…` |

**为什么这样设计**

- **唯一**：`open_id` / `chat_id` 是飞书侧稳定 ID，组合后天然不撞。
- **稳定**：用户改昵称、改群名都不影响 key（昵称会变，ID 不变）。
- **便于路由**：服务器拿到事件后能**纯字符串拼**出 key，O(1) 查会话，不依赖任何模糊匹配。
- **可迁移**：未来上数据库，`session_key` 直接作主键 / 唯一索引，零改造。
- **多租户安全**：前缀 `tenant_key` 保证不同企业租户隔离。

> ⚠️ 与现有 webdock 的对接：当前 webdock 路由用的 key 就是飞书 `open_id`（私聊）。本表的 `session_key` 是「人类可读 + 多类型」的超集，导出给 webdock 时**取 open_id / chat_id 那一段**即可（见 §11）。

- 用户名只能用于**显示**，绝不能用于匹配 / 路由，否则改名即丢历史。

**为什么当前阶段群回复模式默认「仅@回复」**

- 人少阶段，**群里大量是闲聊**，全部送 ChatGPT 既贵又吵、还可能泄露上下文。
- 「仅@回复」=群里只在**显式召唤机器人**时才回复，符合 IM 礼仪，避免机器人插话。
- 全量消息仍然**进日志**（便于以后回看上下文），只是不触发 ChatGPT —— 记录与处理解耦。
- 等规则成熟、成本可控，再按群开「全部回复」。

| @机器人次数 | 数字 | 12 | 否 | 触达 | 群会话看被召唤频率 |
| 备注 | 多行文本 | —— | 否 | 人工标注 | —— |

**关键设计说明**

- **`session_key` + `ChatGPT 对话链接` 是整套系统的命门**：前者是「飞书侧的人 / 群」，后者是「ChatGPT 侧的那条对话」，本表就是这两者的唯一映射。
- **`会话状态 = 待创建`** 是 `/新对话` 的关键状态：服务器或人工发现需要新对话时，把状态置「待创建」、`ChatGPT 对话链接` 置为**项目首页链接**；自动化（webdock）下次收到该 peer 的消息 + `/新对话` 触发，就会**导航到项目首页 → 自动开一条新对话 → 把新对话的 `/c/…` 链接回写本字段**、状态转「活跃」、`会话版本 +1`。这正是你要的「全自动、每次 /新对话 都被记录、对话被匹配」。
- **`是否当前会话` + `会话版本`**：允许同一 peer 保留多条历史会话（归档），但只有 1 条 `是否当前会话=✓` 参与路由。

| 错误信息 | 多行文本 | —— | 否 | 失败详情 | —— |

**为什么群聊消息必须有这 4 个字段（是否@机器人 / 是否需要送ChatGPT / 不处理原因 / 处理状态）**

你的规则是「**群消息全部记录，只有 @ 机器人的才进 ChatGPT**」。要落地这条规则、又要可排查，日志必须能同时表达「我收了 / 我为什么没处理 / 我处理到哪一步」：

- **是否@机器人**：群消息的**第一道闸**。服务器用 `mentions` 字段二次判定（不是看文本里有没有「@」字样，而是看 mentions 里有没有机器人的 open_id），结果固化在这里。
- **是否需要送ChatGPT**：闸门结论。群聊 = `是否@机器人 且 群启用 且 用户启用`；私聊 = 默认真（除非用户禁用）。
- **不处理原因**：为「假」时记原因（未@机器人 / 群禁用 / 用户禁用 / 空消息 / 重复消息），便于回答「这条群消息为什么没回」。
- **处理状态**：群里 99% 的消息会停在 `仅记录`，被@的那条才往下走 `待处理 → … → 已回复`。一眼区分「记录流水」与「处理流水」。

### §6.1 「给 ChatGPT 的输入」模板

```text

```

**群聊模板**（注意：清洗后内容已剔除「@机器人」）

**规则优先级建议（从高到低，先命中先生效）**

```
1. 用户禁用        ← 最高，黑名单一票否决
2. 群禁用          ← 群关机器人
3. 会话暂停        ← 单条会话临时停
4. 会话规则        ← 会话级精调
5. 群规则          ← 群级策略（回复模式/图片/审核）
6. 用户规则        ← 用户级策略（额度/角色）
7. 全局规则        ← 兜底默认
```

> 原则：**禁用类（黑名单）永远高于允许类**，**越具体越优先**（会话 > 群 > 用户 > 全局）。服务器从上往下求值，命中「禁用 / 暂停」立即短路。

## §8 表间关系

```
users ──(1:N)──┐
               ├──> sessions ──(1:N)──> message_logs ──(1:1, 仅需处理的)──> reply_tasks
groups ─(1:N)──┘                              ▲                                  │
                                              └──────(关联会话)──────────────────┘
rules ──(对象类型: 全局/用户/群/会话, 多态关联)──> users / groups / sessions
```

**关联记录 vs 查找引用 vs 冗余文本（关键工程取舍）**

| 用法 | 用在哪 | 为什么 |
|------|--------|--------|
| **关联记录** | sessions.关联用户/关联群；message_logs.关联用户/关联群/匹配会话；reply_tasks.关联消息/关联会话 | 需要双向跳转、需要随主数据更新的「活引用」 |
| **查找引用** | sessions.飞书用户名（←users）；reply_tasks.ChatGPT对话链接（←sessions） | 只读展示，自动跟随源，不想手动维护副本 |
| **冗余文本** | message_logs 的 `发送人 open_id / 发送人名称 / 群 chat_id / 群名称` | **历史快照**：日志是流水账，必须固化当时事实 |

**为什么 message_logs 要冗余存 open_id / 名称 / chat_id / 群名**

- 日志是**历史事实**，不能因为以后用户改名、群改名、甚至用户/群记录被删，导致历史记录失真。
- 排查 / 导出 / 离线分析时，一行日志要**自解释**，不依赖关联表还在不在。
- 关联记录用于「现在的关系」，冗余文本用于「当时的事实」—— 两者并存，各司其职。

## §10 状态流转

### 10.1 message_logs.处理状态

```
                       ┌─ (群未@ / 群禁用 / 用户禁用 / 空 / 重复) ─> 仅记录 (终态)
已接收 ─判定是否送─────┤
                       └─ (需送) ─> 待处理 ─> 处理中 ─> 已送ChatGPT ─> 已回复 (终态)
                                       │                    │
                                       └──────失败──────────┴─> 失败 (可人工重试→待处理)
                                       └─ 人工跳过 ─> 忽略 (终态)
```

| 状态 | 含义 |
|------|------|
| 仅记录 | 群里没@/被禁用等，只入库不处理（群消息的常态） |
| 待处理 | 已判定需送 ChatGPT，已建回复任务，等待执行 |
| 处理中 | 正在送 webdock/ChatGPT |
| 已送ChatGPT | 已投递，等回复 |
| 已回复 | 回复已发回飞书，闭环 |
| 忽略 | 人工决定不处理 |
| 失败 | 出错，待重试 |

### 10.2 reply_tasks.任务状态

```
待复制到ChatGPT ─> 已复制 ─> 待填写回复 ─> 待发送 ─> 已发送 (终态)
                                              │
                                              └─失败─> 失败 ─(重试)─> 待发送
任意态 ─人工取消─> 已取消 (终态)
```

| 状态 | 含义 |
|------|------|
| 待复制到ChatGPT | 任务已建，输入已拼好，等投递（自动化=webdock 取，人工=复制粘贴） |
| 已复制 | 输入已送达 ChatGPT 对话 |
| 待填写回复 | 等 ChatGPT 产出（自动化自动抓，人工手填） |
| 待发送 | 回复已就绪，等回发飞书 |
| 已发送 | 已回飞书，闭环 |
| 失败 | 投递/抓取/回发任一步出错 |
| 已取消 | 人工作废 |

> 自动化（webdock）下，「待复制到ChatGPT → 已复制 → 待填写回复 → 待发送 → 已发送」由程序一步走完；任务表主要价值是**留痕 + 失败时人工接管**。

## §11 服务器写入逻辑（伪代码）

```python
def on_feishu_event(req):
    # 1. 验签（飞书事件 token / encrypt-key）
    if not verify_signature(req):
        return 401

    evt = parse(req)

    # 2. 去重：event_id 优先，message_id 兜底
    if seen(evt.event_id) or seen(evt.message.message_id):
        log_dup(evt)                       # 处理状态=仅记录, 不处理原因=重复消息
        return 200
    mark_seen(evt.event_id, evt.message.message_id)

    # 3. 提取关键字段
    tenant_key  = evt.tenant_key
    chat_type   = evt.message.chat_type           # p2p=私聊 / group=群聊
    open_id     = evt.sender.open_id
    chat_id     = evt.message.chat_id
    msg_type    = evt.message.message_type        # text/image/file/...
    content     = extract_content(evt.message)    # 原始
    mentions    = evt.message.mentions or []       # 关键：@对象列表

    # 4. upsert users / groups（保证主数据存在）
    user  = upsert_user(open_id, sender_name(evt))
    group = upsert_group(chat_id) if chat_type == "group" else None

    # 5. 二次判定是否@机器人（不是看文本，是看 mentions 里有没有 bot 的 open_id）
    at_bot = any(m.id.open_id == BOT_OPEN_ID for m in mentions)
    clean  = strip_bot_mention(content, BOT_OPEN_ID)   # 剔除「@机器人」后的正文

    # 6. 命令识别（/新对话 等），命令以 clean 文本开头判断
    cmd = detect_command(clean)                    # /新对话 / /重置 / /摘要 / None

    # 7. 判定是否需要送 ChatGPT
    need_gpt, reason = decide(chat_type, at_bot, user, group)
    #   私聊: 用户启用 -> True；用户禁用 -> False(用户禁用)
    #   群聊: at_bot 且 群启用 且 用户启用 -> True；否则 False(未@机器人/群禁用/用户禁用)
    #   空 clean -> False(空消息)

    # 8. 写消息日志（无论是否处理，全部落库；冗余固化 open_id/名称/chat_id/群名）
    log = create_message_log(
        message_id=evt.message.message_id, event_id=evt.event_id, tenant_key=tenant_key,
        chat_type=chat_type, sender_open_id=open_id, sender_name=user.name,
        chat_id=chat_id, group_name=(group.name if group else None),
        msg_type=msg_type, raw=content, clean=clean,
        at_bot=at_bot, mentions=mentions, is_command=bool(cmd), command=cmd,
        need_gpt=need_gpt, reason=(None if need_gpt else reason),
        status=("待处理" if need_gpt else "仅记录"),
        raw_json=evt.raw,
    )

    # 9. 不需要处理 -> 结束（群里绝大多数走这里）
    if not need_gpt:
        return 200

    # 10. 需要处理 -> 找/建会话索引 -> 建回复任务
    session_key = build_session_key(tenant_key, chat_type, chat_id, open_id)  # 见 §1
    session = find_session(session_key) or create_session(session_key, ...,
                  status="待创建", link=PROJECT_HOME_URL)   # 新 peer 默认待创建

    if cmd == "/新对话":
        session.status = "待创建"            # 触发下次导航到项目首页开新对话
        session.link   = PROJECT_HOME_URL
        session.version += 1

    task = create_reply_task(
        message=log, session=session,
        task_type=("新建会话" if cmd == "/新对话" else "普通回复"),
        status="待复制到ChatGPT",
        gpt_input=render_template(chat_type, user, group, clean),  # §6.1 模板
    )
    log.matched_session = session
    enqueue(task)                            # 交给 webdock 自动执行
    return 200
```

**`/新对话` 的自动闭环（你要的「全自动、链接被记录、对话被匹配」）**

1. 服务器识别 `/新对话` → 会话置「待创建」、link=项目首页、版本+1、建「新建会话」任务。
2. webdock 拿到该 peer 的请求 + force_new → **导航到项目首页 → ChatGPT 自动开一条新对话** → 抓到新对话 `/c/…` 链接。
3. webdock 把新链接**回写**会话索引表「ChatGPT 对话链接」、状态转「活跃」。
4. 之后该 peer 的普通消息 → 路由到这条新链接，对话被正确匹配。

## §11′ 与现有运行系统对接（重要：这是 `/新对话` 失效的根治）

**现状链路**：飞书消息 → OpenClaw 网关 → `openclaw-bridge`(:18080) → `webdock`(:11800, 驱动 ChatGPT 网页) → 回程。webdock 用 `feishu_projects.json` 决定每个飞书 peer 路由到哪个项目，用 `lane_state.json` 记每个 peer 当前的 `/c/…` 对话。

**为什么现在 `/新对话` 不新建对话**：`feishu_projects.json` 现在是 `{"lanes":{}}`（空），webdock 对飞书 peer 查不到 `project_url`，`/新对话(force_new)` 没有项目首页可导航 → 直接停在 `lane_state` 里那条旧 `/c/…` 对话上，永远不新建。**根因不是触发没识别（识别是好的），是路由没配。**

**本设计如何根治**：会话索引表就是缺失的「飞书 peer → 项目」路由源。落地两步：

1. **导出映射**：把会话索引表中「会话状态∈{活跃,待创建} 且 是否当前会话=✓」的行，导出为 webdock 认的格式：
   ```json
   {"lanes": {
     "<open_id 或 chat_id>": {"name": "<飞书用户名/群名>", "project_url": "https://chatgpt.com/g/g-p-6a2ffe0bac248191988612d9081dd6b1-lark-hao/project"}
   }}
   ```
   key 取 session_key 里的 `open_id`（私聊）/ `chat_id`（群）那一段，`project_url` 用**项目首页**链接（带 `/project`，force_new 导航到它才会开新对话）。

2. **喂给运行时**：让这份 JSON 进到 backend 的 `/v1/routing/feishu-projects.json`，webdock 的拉取器（已修，每 60s 拉一次）就会写进 `feishu_projects.json`、`LaneRouter` 热重载生效。之后飞书 `/新对话` 即可在项目里自动开新对话并回写链接。

> ⚠️ 注意：webdock 拉取器现在是好的（本轮已修 urlopen bug），它会**每 60s 用 backend 的值覆盖** `feishu_projects.json`。所以**手动塞本地文件活不过 60s**，必须从 backend 路由源（= 本管理台导出 / 或企微表的飞书工作表）喂。

**立刻能让 `/新对话` 跑起来的最小动作**（在 Bitable 自动同步管线建好之前）：把当前飞书用户（如 hao=`ou_28d4f058…`）一行 `{open_id → lark-hao 项目首页}` 加进 backend 飞书路由源即可；之后再切到管理台驱动。
```
